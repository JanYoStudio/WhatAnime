## 存放位置

| 内容 | 位置 | 是否进入 Git |
| --- | --- | --- |
| 长期有效的架构、维护、开发与测试说明 | `docs/`，必要时按主题建子目录 | 是 |
| 设计文档、实施计划 | `docs/plans/` | 是 |
| 临时草稿、调查笔记、执行/验证报告、审查结果、日志、临时截图 | 系统临时目录下按任务隔离的子目录 | 否 |
| 构建工具固定输出的测试报告、生成物 | 既有且已忽略的构建输出目录 | 否 |

系统临时目录通过平台能力获取：Windows 的 `$env:TEMP`、Python 的 `tempfile.gettempdir()` 等；不要硬编码用户名或本机路径。临时文件可能被系统清理，不得成为正式文档唯一的依据或必需链接。需要长期保留的决策应整理进正式设计，而不是把报告整体搬入仓库。

根目录的 `README.md`、`AGENTS.md`、`CLAUDE.md`、`CHANGELOG.md`、许可证等属于仓库入口、工具入口或发行约定，保留现有位置；新增专题文档放在 `docs/`，不再另建根目录文档体系。`CLAUDE.md` 保持仅导入 `AGENTS.md`。

## 命名与文档关系

- 专题设计：`YYYY-MM-DD-<topic>-design.md`。
- 配套 UI 规范：`YYYY-MM-DD-<topic>-ui-spec.md`。
- 实施计划：`YYYY-MM-DD-<topic>-implementation-plan.md`。
- 日期采用初次成文日期，后续修订更新文档内状态，不反复复制同一主题的近似版本。
- 一个主题指定一个整体设计入口；配套规范只维护自身职责，避免在多处复制状态机、接口或验收规则。
- 新增长期文档时更新本索引。使用仓库相对链接，不链接系统临时文件、个人目录或某个代理会话。

## 内容与生命周期

设计文档至少说明：状态、目标与非目标、现状依据、设计决策、行为及数据契约、影响范围、验收标准和未验证的技术风险。UI 规范说明视觉与交互；整体设计补齐工程契约。实施计划说明任务顺序、依赖、测试和交付检查点，不用计划反向修改未确认的需求。

状态须明确区分：

1. **草案／待确认**：可供评审，不代表实施授权。
2. **已确认设计**：记录确认的范围；只有用户授权后才进入相应计划或实现阶段。
3. **实施中**：保持设计与实际决策一致，不能把待测试能力写成已通过。
4. **已实施**：有对应实现与验证证据；仍有平台限制时明确保留。
5. **已替代**：链接后续设计，不使旧文档继续冒充当前规范。

用户认可设计方向，不等于确认尚未形成的完整设计文档；设计、计划、实现、提交和发布的授权不互相替代。

## 审查与验证

- 持久化文档用中文，标识符保留源码形式；现状事实、目标行为和待实测项分别标注。
- 不包含凭据、个人设备信息、本机绝对路径、临时批次/会话 ID、原始调试日志或一次性过程记录。
- 审查意见及过程保存在系统临时目录；采纳的结论直接修订到文档对应章节。
- 纯文档修改核对相对链接、引用路径、命名、状态与前后契约，并执行 `git diff --check`，无需运行 Gradle。
- 单元测试、编译、设备实测和真实 API 验证分别记录结果，不互相替代；临时结果不作为正式文档附件提交。
